## 1. Verdict: is the forecast database-driven?

**No. The forecast engine is CSV-driven with hand-curated factor constants; database evidence informs — and today cannot even inform — only narrative prose.**

1. **The math path reads no database at all.** Every probability, seat projection and scenario number derives from exactly five canonical CSVs, all present and resolved through the real `data_roots` resolver:
   - `data/canonical/research/federal/ge16-projection-model.csv` (baseline winner/runner-up/margin)
   - `data/canonical/research/derived/ge15-results-by-constituency-full.csv` (state keying)
   - `data/canonical/research/derived/voter-demographics-by-constituency-ge15.csv` (ethnic/youth modulation)
   - `data/canonical/research/derived/swing_se_to_se.csv` (state swings)
   - `data/canonical/research/derived/swing_boundary_grouped.csv` (per-parliament DUN-boundary swings — present, though absent from the parent's lead list)
   plus imported constants from `analytics/engine/config.py` (`FACTORS`, `MACRO`, and `EVENT_SHOCKS`, which is **empty**).

2. **The events DB reaches the math only through human curation.** `config.py:42-64` is explicit: `EVENT_SHOCKS` is a hand-curated mapping, "Reviewed 2026-09-24 against `work/events/ge16-events.db`; removals below" — and the review's outcome was to remove every shock. No runtime code reads any events DB into the model. This confirms the packet's lead: the DB informed the *curation decision*, not the arithmetic.

3. **The subsystem's only DB readers are narrative-side, and they are dangling.** `report_builder.py:119/243` (`sqlite3.connect(...mode=ro)`) read the story ledger for report §2.1, state scoping (T1.5) and reference-pack story claims — all classification (b). They target `ROOT/work/events/ge16-events.db`, which does not exist at the V3 root; the `os.path.exists` guards fail closed to the "ledger not built" honest line. `reference_pack.py:599` answers the packet's specific question: it is a **provenance label string** (`work/events/ge16-events.db#v_story_current`) attached to claims whose underlying data comes from that same dangling read.

4. **The live canonical events DB is BESIDE the engine.** `data/canonical/events/ge16-events.db` (512 events, 117 stories; P2.8 baseline + additive-merge machinery, verified on disk) has **zero readers** under `analytics/engine/**`. The 512-event evidence base is stored beside the analysis, not read by it. Same for the frozen `ge16-events-p25-baseline.db` (+sha256 sidecar).

5. **The report/pack/authoring layer is anchored on the absent V2 output tree.** `02_FORECAST/`, `work/`, `03_REPORTS/`, `05_AUTOMATION/` do not exist at the V3 root. Four **unguarded** reads crash their CLIs outright in V3: `report_builder.py:71` (FORECAST_JSON), `report_builder.py:919` (SCENARIOS), `reference_pack.py:703` and `:984` (SCENARIOS). Guarded reads degrade (state-report Tier-1 sections lose the forecast/scenario layer; fingerprint DB resets; smart-scan rebuilds everything). This is the recorded P4-class baseline, not a defect to fix here.

**Permitted claim going forward:** "the model math is driven by five canonical CSVs plus reviewed config constants; the events database currently supports no runtime path — its evidence enters via human review of shocks and (once P3.2/P4 resolve the ledger path) narrative prose."
